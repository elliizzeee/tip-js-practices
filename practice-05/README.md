## Эксперимент с очередями выполнения

До запуска `npm run example:order` записать прогноз порядка меток. После запуска внести фактический порядок и объяснить каждую позицию.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Весь синхронный код выполняется первым: A — начало, B — вход в async-функцию до первого `await`, C — конец синхронного блока. `await null` и `Promise.resolve().then` ставят продолжения в очередь микрозадач: сначала D (поставлена раньше), затем E. Таймер F идёт в очередь макрозадач и выполняется последним. |
| Фактический результат | A, B, C, D, E, F | Совпадает с прогнозом: `npm run example:order` вывел метки именно в таком порядке. |


-Синхронный код: A (начало), B (вход в async-функцию до первого await), C (конец синхронного блока)

-Очередь микрозадач: D (обработчик Promise.then), E (продолжение после await null). Выполняются после синхронного кода, до макрозадач, в порядке постановки

-Таймер с задержкой 0: F попадает в очередь макрозадач и выполняется только после того, как стек вызовов пуст и все микрозадачи обработаны. «0 мс» — это минимальная задержка, а не немедленный вызов

-Если удалить один обработчик Promise: порядок оставшихся меток не изменится, просто пропадёт соответствующая буква (D или E). Место таймера F относительно синхронного кода и оставшихся микрозадач сохранится

## Организация кода


| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP-API: маршруты, фильтры, CORS, HEAD/OPTIONS, структурированные ошибки. В работе не изменялся. |
| `src/api-client.js` | Транспортный слой: `buildUrl`, `createApiClient`, `requestJson`, класс `ApiError`, тайм-аут, отмена, разбор JSON, классификация ошибок. Доменных правил не содержит. |
| `src/task-api.js` | Доменный слой: валидация входных фильтров и id, проверка ответов по схеме (задача, категория, список, `meta`), методы `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`. |
| `src/variant.js` | Данные индивидуального варианта: `variantNumber = 1`, `variantFilters = {completed: false, priority: "high"}`. |
| `src/main.js` | CLI-клиент: читает `API_URL`, создаёт клиент и доменный API, вызывает `loadInitialData` с фильтрами варианта, печатает id и `meta`, различает ошибки по `kind`. |

fetchFn передаётся в createApiClient — чтобы модульные проверки могли подменить сеть без реального HTTP, а также чтобы клиент не зависел от глобального fetch и был тестируемым.

HTTP-ошибки проверяются отдельно от сетевых — это разные причины: HTTP-ошибка означает, что сервер ответил (есть status, code, details), а сетевая ошибка означает, что ответа не было вовсе (fetch бросил исключение). Смешивать их — значит терять информацию для обработки.

JSON после разбора всё равно проверяется по контракту — сервер может вернуть валидный JSON с неверной структурой (нет data, неверные типы, повторяющиеся id, несовпадение meta.total). Только схема гарантирует, что вызывающий код получит предсказуемые данные.

## Реализация общего клиента


| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | Обрезка хвостовых `/`, проверка абсолютного URL, разрешены только `http`/`https`, запрещены `query`/`hash` | `buildUrl("http://127.0.0.1:5505/api/", "/tasks")` → `http://127.0.0.1:5505/api/tasks` |
| Кодирование query-параметров | `URL.searchParams.set(name, String(value))`, пропуск `undefined`/`null`/`""`, сохранение `false` и `0` | Тест 02: `false` → `"false"`, `0` → `"0"`, `"API & ошибки"` кодируется |
| Заголовок `Accept` | `headers: {Accept: "application/json"}` в каждом запросе | Тест 05: `new Headers(options.headers).get("accept") === "application/json"` |
| Проверка `response.ok` | При `!response.ok` — попытка прочитать `{error}` из JSON, формирование `ApiError` с `status`/`code`/`details` | Тесты 08, 09, 16 |
| Проверка `Content-Type` | Регулярное выражение `/^application\/json\b/i` для успешных ответов; иначе `invalid-response` | Тесты 10, 11 |
| Разбор JSON | `response.json()` в `try/catch`, `SyntaxError` → `cause` у `ApiError` | Тест 11: `error.cause instanceof SyntaxError` |
| Ограничение времени | `AbortController` + `setTimeout` на `timeoutMs` (по умолчанию 10 000, можно переопределить в вызове) | Тест 14: `kind === "timeout"` |
| Внешняя отмена | Объединение внешнего `signal` с внутренним через `AbortSignal.any`, различение `timeout`/`aborted` | Тест 15: `kind === "aborted"` |

## Последовательная и параллельная загрузка

Сравнить два сценария получения задач и категорий через `/debug/delay`. Каждый сценарий выполнить минимум три раза с одинаковыми задержками.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 312 | 318 | 305 | Время ≈ сумме задержек (`/tasks` ~150 + `/categories` ~150) |
| `Promise.all` | 158 | 162 | 155 | Время ≈ максимуму задержек, оба запроса идут одновременно |

Измерения зависят от компьютера и не сравниваются с чужими значениями. В выводе требуется объяснить причинную связь, а не заявлять точное ускорение для любых условий:

Причинная связь: при последовательных await второй запрос стартует только после завершения первого, поэтому общее время складывается из задержек. При Promise.all оба запроса запускаются до первого await, и общее время определяется более медленным из них. Точное ускорение зависит от задержек и машины, поэтому сравнивать с чужими числами нельзя — важен сам факт: параллельный запуск не ждёт поочерёдно

до fetchFn(...) — проверить URL и заголовки;

после получения Response — status, ok, headers.get("content-type");

в catch — error.kind, error.status, error.cause.

## Вывод

Реализован клиент, который корректно работает с локальным API: собирает URL, кодирует query, ставит Accept, различает успешные ответы, HTTP-ошибки, сетевые сбои, неверный формат ответа, тайм-аут и явную отмену. Доменный слой проверяет входные фильтры и ответы по схеме, поэтому неверные данные не попадают в вызывающий код.

Ключевые различия:

Ожидание Promise — это не ошибка, а нормальное состояние: запрос ещё выполняется.

HTTP-ошибка — сервер ответил, но статус вне 2xx; есть status, code, details.

Сетевая ошибка — ответа не было (fetch бросил исключение); status отсутствует.

Неверный ответ сервера — статус 2xx, но Content-Type не JSON, битый JSON или структура не соответствует контракту.

Тайм-аут — запрос не уложился в timeoutMs, сработал внутренний AbortController.

Явная отмена — вызывающий код вызвал abort() на внешнем AbortController.

Все 18 проверок API, 26 модульных и 13 интеграционных проверок проходят. Вариант 1: фильтр {completed: false, priority: "high"} возвращает id [4, 13, 34], meta.total = 3 — совпадает с ожидаемым
