## 1. Цель работы

Отработать подключение браузерного приложения к учебному HTTP API: реализовать клиент с поддержкой GET, POST, PATCH и DELETE, доменный слой задач с проверкой схемы ответа, состояния интерфейса и защиту от устаревших ответов при смене фильтров. В результате приложение загружает, создаёт, редактирует, переключает статус и удаляет задачи только через HTTP, а после перезапуска API восстанавливается исходный набор

## 3. Реализация

### 3.1. HTTP-клиент

requestJson поддерживает GET, POST, PATCH, DELETE. Для тела выполняется JSON.stringify и добавляется Content-Type: application/json; у GET тело запрещено, и Content-Type без тела не ставится. Ответ 204 возвращается как null без попытки разбора JSON. HTTP-ошибка проверяется до Content-Type успешного ответа. Тайм-аут реализован через внутренний AbortController, внешняя отмена — через переданный signal; оба объединяются через AbortSignal.any, чтобы различать timeout и aborted

### 3.2. Доменный API

Реализованы операции: getTasks, getTaskById, getCategories, loadInitialData, createTask, updateTask, setTaskCompleted, deleteTask, resetDemoData. Каждый метод принимает { signal }. Схема ответа проверяется в task-api.js: isTask, isCategory, assertTaskList (уникальность id, совпадение meta.total), assertTask, assertCategory. Неверная схема → ApiError с kind: "invalid-response"

### 3.3. Состояния интерфейса

Контроллер переключает состояния loading, ready, empty, error. При загрузке показывается loading и aria-busy="true". Успешный ответ с задачами → ready; пустой список → empty; ошибка → error с кнопкой повтора. При повторной загрузке предыдущий запрос отменяется через AbortController, устаревший ответ игнорируется по счётчику loadSeq

### 3.4. Изменение данных

Создание, редактирование, смена статуса, удаление и сброс выполняются через доменный API. После успешной мутации контроллер повторно запрашивает список с текущими фильтрами, поэтому интерфейс показывает данные сервера, а не локальную копию. На время мутации действия блокируются через setMutationPending

### 3.5. Защита от устаревшего ответа

Перед новой загрузкой контроллер вызывает abort() на предыдущем AbortController и увеличивает loadSeq. Ответ с устаревшим seq не применяется к интерфейсу. Ошибка отменённого запроса (kind: "aborted") не показывается пользователю

## 6. Ответы на контрольные вопросы

1. _Почему `fetch` не отклоняет Promise при ответе 404?_
   _Почему fetch не отклоняет Promise при ответе 404?
fetch отклоняет Promise только при сетевой ошибке (нет соединения, DNS, обрыв). HTTP-статус 404 — это успешно полученный ответ, поэтому Promise выполняется, а response.ok равно false. Ошибку нужно проверять вручную по response.status_
2. _Почему ответ 204 нельзя разбирать вызовом `response.json()`?_
   _Почему ответ 204 нельзя разбирать вызовом response.json()?
У 204 нет тела по спецификации. response.json() попытается прочитать пустой поток и бросит SyntaxError. Поэтому клиент сначала проверяет status === 204 и возвращает null_
3. _Чем состояние `empty` отличается от `error`?_
   _Чем состояние empty отличается от error?
empty — запрос успешен, но данных по фильтру нет (например, поиск не дал результатов). error — запрос не выполнен: сеть, тайм-аут, HTTP-ошибка или неверный формат ответа. В empty нет кнопки повтора, в error она есть_
4. _Зачем отменять предыдущий запрос при смене фильтров?_
   _Зачем отменять предыдущий запрос при смене фильтров?
Чтобы устаревший ответ не перезаписал более новый. Если пользователь быстро меняет фильтры, ответы могут прийти не в том порядке. AbortController отменяет предыдущий запрос, а loadSeq дополнительно отбрасывает устаревшие ответы, если отмена не успела_
5. _Почему после мутации список повторно запрашивается у API?_
   _Почему после мутации список повторно запрашивается у API?
Чтобы интерфейс показывал данные сервера, а не локальную копию. Сервер назначает id, применяет сортировку и фильтры, может отклонить часть изменений. Повторный запрос гарантирует, что список соответствует состоянию сервера_

## 7. Вывод

Браузерный интерфейс связан с API через три слоя: api-client.js отвечает за транспорт, task-api.js — за контракт и схему, app-controller.js — за состояния и последовательность действий. Интерфейс не обращается к fetch напрямую и не хранит данные в localStorage: единственный источник данных — учебный API.

Найденные и исправленные ошибки: в первой версии клиента внешний AbortSignal не объединялся с внутренним, из-за чего тайм-аут маскировался как aborted; после добавления AbortSignal.any и разделения timeout/aborted тест 12 проходит. Также в первой версии requestJson не проверял, что fetchFn вернул Response; после добавления isResponse тест 12 модульных проверок проходит. В контроллере первая версия не отменяла предыдущую загрузку при смене фильтров; после добавления AbortController и loadSeq тест 27 проходит
